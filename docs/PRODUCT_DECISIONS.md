## Implementation defaults for this milestone

These choices let implementation proceed and can be revised when evidence warrants it. They do not imply user approval of a final public name, source license, or minimum hardware specification.

| Decision | Default and rationale |
| --- | --- |
| Working title | **Parkbound**, a temporary original-name proposal. Availability and trademark clearance have not been checked; do not publish under this name without review. Local directory names are workspace labels, not public branding. |
| Play model | Offline single-player with local saves. A downloadable build should remain playable without a service account or an active server. |
| First build target | Windows 11 x64. The development-machine version and actual executable verification belong in each build report; this is not yet a minimum Windows requirement. |
| Engine candidate | Bevy 0.17.3, deliberately pinned for the selected Rust 1.93.1 toolchain and API compatibility; it is not presented as the newest release. Stage 2 proves rendering, selection, crowd simulation, and coaster behavior before large-scale content production. |
| Core boundary | A window-independent Rust simulation owns authoritative state; the game layer handles rendering, input, UI, and audio. Content definitions use stable identifiers. |
| Simulation contract | Fixed ticks, explicit update order, seeded randomness, integer money, and validated atomic commands. Same-build reproducibility is tested before claiming it. |
| Visual direction | Original isometric park art and interface, with four view orientations as the completed target. Simple geometric placeholder art is acceptable for the first executable. |
| Historical first deliverable | The 0.1.0 foundation was a 32 × 32 isometric map, camera/selection, toolbar/status, simulation clock, pause/speed, and packaged executable. Later named checkpoints add guests, a train, persistence, paths, and single-tile terrain editing; none alone completes the full management game. |
| Retained overlap baseline | Version 0.3.0 established the original 12-segment elevated walkway and nine track tiles. Version 0.4.0 extends the walkway into 37 path nodes at height 8, with track retained at height 0; clearance remains 2. T preserves time, materials, object IDs/heights, and guests. Flat exposes the same track. |
| Path connectivity | Compatible opposing cardinal edges must have identical endpoint heights; ramps expose only their two opposite ends. The public navigation graph excludes queue paths. In 0.15.0, ordinary and Approaching guest routes use only that public graph. Admitted/Leaving guests additionally follow their own queue through a separate ordered/reserved state machine. Owned queues retain the same Flat/ramp edge geometry. Queue/gate edits do not invalidate the public path cache; public edits retain normal invalidation. |
| Crowd proof | Twelve seeded guests choose reachable path destinations using deterministic BFS and stored SplitMix64 state. Each edge takes 30 ticks; guests dwell for 30 ticks at arrival. All simulation progress uses integers; rendering only presents it. These ordinary path arrivals remain distinct from queue admission events and completed rides; neither counter represents revenue. |
| Removal and recovery | Visible-path demolition clears affected routes immediately. The 0.13.0 contract retains base/footprint slope in anchor_slope and limits recovery to compatible local paths rather than arbitrary nearest destinations. R restores fixture paths atomically with fresh IDs, preserving player pieces/time/RNG/guests. Slope removal/recovery and migration passed release regressions and production continuation; native X demolition and Backup restoration of a saved ramp passed. |
| Complete ticks | The fixed update remains 30 Hz. Normal/fast/fastest run one/two/four complete authoritative steps; pause runs none. New moving systems must join the complete step rather than multiplying only the clock. |
| Guest presentation | A separate procedural mesh follows authoritative path progress through shared fixed-point piecewise surface samples. Slope height varies within a tile; base-height interpolation alone is insufficient. A retained anchor_slope supports local lost/recovery positioning after demolition. Slope sampling passed release regressions, production continuation, and visual checks in Surface/Underground views; guests remain nonselectable original geometry. |
| Train circuit | One original closed station/lift/drop/brake circuit with three cars, rail heights 8–16, and shared sampled integer centerlines for movement and rendering. The fixed circuit gains passengers in 0.16.0; it is not a track editor or a complete configurable ride catalogue. |
| Train motion | 1024 distance units per tile/height step; arc length scales a vertical step to one quarter tile. Integer tick rules bound the lift, accelerate the descent, and reduce speed in brakes. These are tuned demonstration rules, not real coaster physics or safety ratings. |
| Train operation | The empty train retains the original 90-tick station dwell and Open/Close finish-lap behavior. Version 0.16.0 adds holds for physical boarding/exiting and completed-lap passengers awaiting an exit. Global pause freezes train, guests and transfers. F/Find focuses the circuit. One station transfer runs at a time; boarding uses the lowest free seat and its completion resets the open train's 90-tick dwell. |
| Train clearance and presentation | Rail envelopes participate in shared placement/terrain validation; camera fit includes sampled rail height. Track rendering/picking uses real sampled faces, not clearance roofs. Cars use a separate nonselectable mesh. Decorative supports are omitted where they intersect other occupied objects; physical support reservations are deferred. |
| Terrain height units | `park_sim` stores integer steps and validates a maximum of 32. The current renderer maps one step to 16 world units. This display conversion belongs to presentation; it is not a physical metre or a promised final clearance rule. |
| Selectable identity and visibility | Terrain uses `SurfaceId::Terrain(TilePos)`; each path/track object uses `SurfaceId::Object(ObjectId)`. IDs are stable and never reused. U/the visibility button switches Surface and Underground views. Buried track is excluded from ordinary picking; Underground removes terrain from rendering and picking and uses a non-selectable reference floor. |
| Clearance proof | Objects occupy one tile and a half-open integer interval `[height, height + clearance)`, within 0–32. Touching intervals may stack; overlapping ones are rejected atomically. Paths must be on/above terrain; track must be on/above terrain or fully buried. Terrain edits/presets must preserve these invariants. One-step path slopes reserve clearance 3; level paths reserve 2. Land rights, terrain slopes, water-volume rules, and construction costs remain later work. |
